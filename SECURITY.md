# Security Policy

Thank you for helping keep SpinQICK and its users secure.

If you believe you have found a security vulnerability in this repository, please report it privately so we can investigate and address it responsibly.

## Reporting a Vulnerability

Please **do not** report security vulnerabilities through public GitHub issues, pull requests, or discussions.

Instead, email:

**dl.foss-disclosure@hrl.com**

Please include, to the extent possible:

- a short description of the issue
- the affected component, version, or commit
- steps to reproduce the issue
- the potential impact
- any suggested mitigation or fix
- your preferred name for acknowledgment, if any

Please send only the minimum information needed to understand and reproduce the issue.

## Sensitive Data

Do **not** include secrets, credentials, private keys, personal data, export-controlled information, or other sensitive material in your report.

If you encounter sensitive data while testing, please:

1. stop testing immediately,
2. do not retain, copy, or share the data beyond what is strictly necessary to report the issue, and
3. notify us right away at **dl.foss-disclosure@hrl.com**.

## Scope

This policy applies to the SpinQICK open-source repository and code distributed from it.

If an issue is primarily in a third-party dependency, upstream project, local lab environment, or custom deployment, please report it to the appropriate maintainer as well. You are welcome to notify us if the issue may affect SpinQICK users.

## Our Response Process

We will make a good-faith effort to:

- acknowledge receipt of your report within **5 business days**
- review and triage the report
- contact you if we need more information
- keep you informed of material status changes as we work on remediation

Remediation timelines depend on severity, impact, reproducibility, and maintainer availability.

## Coordinated Disclosure

We ask that you avoid public disclosure until we have had a reasonable opportunity to investigate and, where appropriate, provide a fix or mitigation.

If we confirm the issue, we may publish a security advisory, release notes, or other notice when a fix or mitigation is available. Unless a different timeline is needed to protect users, our preference is that public disclosure occur **no sooner than 30 days after a fix or mitigation is publicly available**, or on a mutually agreed timeline.

## Good-Faith Research / Safe Harbor

If you act in good faith and follow this policy, we will consider your research to be authorized.

In particular, please:

- avoid privacy violations, service disruption, and destruction or modification of data
- use only the minimum testing necessary to confirm the issue
- do not exfiltrate data
- do not establish persistence, pivot to other systems, or attempt denial-of-service
- do not use social engineering, phishing, physical intrusion, or other non-technical attacks
- stop and report immediately if you access sensitive data or believe testing may cause harm

We do not intend to pursue legal action against researchers for good-faith security research that is consistent with this policy.

## Supported Versions

Security fixes are prioritized for the latest supported release and the current main development branch. In some cases, users may be asked to upgrade to receive a fix.

## Non-Security Issues

For bug reports, feature requests, documentation issues, or general support questions, please use the normal GitHub project channels rather than the disclosure email address.
